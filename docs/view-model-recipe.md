# Hakoniwa View Model Recipe

## Purpose

`viewer.recipe.yaml` is the human-authored input used to generate a Hakoniwa view-model from an MJCF file.

The generated view-model is a view-only manifest. The recipe is the small amount of human intent needed to decide which MJCF bodies and joints should appear in that view-model.

```text
MJCF + viewer.recipe.yaml -> view-model.json
```

The recipe is not a runtime configuration file. It must not describe communication, control, sensors, actuators, or downstream runtime behavior.

## Relationship to view-model

`viewer.recipe.yaml` is the input contract.

`view-model.json` is the generated output contract.

```text
viewer.recipe.yaml
  - selects the robot root body
  - selects movable joints
  - selects fixed bodies
  - declares visual asset mapping rules

view-model.json
  - contains generated body / joint / asset mapping
  - is consumed by downstream viewers or runtime adapters
```

The authoritative robot body structure remains in the MJCF. The recipe should only add selection and mapping intent that is not safe to infer automatically.

## Recommended placement

```text
bodies/<robot>/config/viewer.recipe.yaml
bodies/<robot>/generated/<model>.xml
bodies/<robot>/generated/parts/*.glb
bodies/<robot>/generated/view-model.json
```

The recipe should point to the structural MJCF generated by `urdf2mjcf.py`.

It should not point to an actuated or runtime-customized MJCF unless the view-model generator explicitly needs information that exists only there. In the normal mbody flow, actuator-specific MJCF files belong outside `hakoniwa-mbody-registry`.

## Current example

```yaml
format: hako_viewer_model_recipe
version: 0.1

robot: turtlebot3_burger
mjcf: ../generated/turtlebot3_burger.xml

assets:
  glb_dir: parts
  map: body_name

base: base_link

movables:
  - wheel_left_joint
  - wheel_right_joint

fixed_bodies:
  - base_scan
```

## Fields

### `format`

Required.

Format identifier for the recipe.

Current value:

```yaml
format: hako_viewer_model_recipe
```

### `version`

Required.

Recipe schema version.

```yaml
version: 0.1
```

### `robot`

Optional but recommended.

Robot name to emit into the generated view-model.

If omitted, the generator may use the MJCF model name or the MJCF filename stem.

```yaml
robot: turtlebot3_burger
```

### `mjcf`

Required.

Path to the structural MJCF file used as the source body model. Relative paths are resolved from the recipe file directory.

```yaml
mjcf: ../generated/turtlebot3_burger.xml
```

### `assets`

Required.

Visual asset mapping configuration.

```yaml
assets:
  glb_dir: parts
  map: body_name
```

#### `assets.glb_dir`

Directory containing generated GLB files. The path is emitted into the generated view-model asset paths.

```yaml
assets:
  glb_dir: parts
```

#### `assets.map`

Mapping rule from MJCF body names to GLB asset names.

Current supported value:

```yaml
assets:
  map: body_name
```

With `body_name`, a body named `wheel_left_link` maps to:

```text
parts/wheel_left_link.glb
```

### `base`

Required.

MJCF body name used as the view root.

```yaml
base: base_link
```

The generated view-model uses this body as `robot.root` and emits it as the `base` part with an identity mount.

### `movables` / `movable_joints`

Optional.

List of MJCF joint names that should be emitted as movable visual parts.

```yaml
movables:
  - wheel_left_joint
  - wheel_right_joint
```

`movable_joints` is also accepted as a more explicit alias:

```yaml
movable_joints:
  - wheel_left_joint
  - wheel_right_joint
```

Each listed joint is resolved through the MJCF. The generator emits the body that owns that joint as a `movable_parts[]` entry.

The resulting motion metadata is derived from the MJCF joint type and axis. It is for view-side reconstruction only and does not define actuator or control behavior.

### `fixed_bodies`

Optional.

List of MJCF body names that should be emitted as fixed visual parts.

```yaml
fixed_bodies:
  - base_scan
```

Use this for visual parts that should appear in the view-model but are not driven by a joint.

### `coordinate_system` / `coordinate`

Optional.

Coordinate system metadata to emit into the generated view-model.

```yaml
coordinate_system: ros
```

The shorter key is also accepted for compatibility:

```yaml
coordinate: ros
```

If omitted, the generator currently defaults to `ros`.

## Non-goals

The recipe must not contain:

- PDU channel definitions
- endpoint configuration
- shared-memory paths
- actuator parameters
- sensor runtime configuration
- controller settings
- Godot `NodePath`
- Godot `.tscn` output paths
- GDScript names
- MuJoCo runtime or solver parameters

If a downstream runtime needs those values, define them in a runtime-specific config or profile outside the mbody view-model recipe.

## Validation rules

A generator should validate at least the following:

- `format` is `hako_viewer_model_recipe`
- `version` is supported
- `mjcf` exists
- `assets.map` is supported
- `base` exists as an MJCF body
- every `movables[]` or `movable_joints[]` item exists as an MJCF joint
- every `fixed_bodies[]` item exists as an MJCF body
- generated asset paths are deterministic

## Design rule

```text
recipe selects view intent.
view-model records generated view structure.
MJCF remains the canonical body model.
runtime-specific configuration stays outside the recipe.
```
